### 4.1 🔴 CRITICAL — `cardView: "guitar"` / `"tablature"` ломает автосохранение проекта целиком

**Проверено лично, воспроизведено исполняемым probe-скриптом.**

**Механизм.** UI умеет переключать вид карточки матрицы в Guitar, а `cardView` шага пишется в портируемый JSON как есть — но JSON-схема допускает только три значения.

| Звено                   | Файл:строка                                                                       | Факт                                                                                |
| ----------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Тип в домене            | `src/domain/progression/step.ts:7`                                                | `CardViewId = "harmonic" \| "piano" \| "staff" \| "guitar" \| "tablature"`          |
| UI предлагает Guitar    | `src/ui/matrix/HarmonicMatrix.tsx:405`                                            | `availableViews={["harmonic", "piano", "staff", "guitar"]}`                         |
| Запись глобального вида | `src/app/commands/matrixViewCommands.ts:28`                                       | `globalMatrixCardView: command.payload.view`                                        |
| Наследование шагом      | `src/app/commands/matrixCommands.ts:69`                                           | `cardView: template?.cardViewOverride ?? project.presentation.globalMatrixCardView` |
| Сериализация            | `src/persistence/portableProject.ts:384`                                          | `cardView: step.cardView`                                                           |
| Валидация перед записью | `src/persistence/portableProject.ts:573-582`                                      | при невалидности — `throw InvalidPortableProjectError`                              |
| **Схема**               | `specs/001-cadenceflow-core-studio/contracts/cadenceflow-project.schema.json:256` | `"cardView": { "enum": ["harmonic", "piano", "staff"] }`                            |

**Доказательство.** Минимальный валидный документ, где меняется **только** `cardView`:

```
cardView=harmonic    total=12  new-vs-baseline=none
cardView=piano       total=12  new-vs-baseline=none
cardView=staff       total=12  new-vs-baseline=none
cardView=guitar      total=13  new-vs-baseline=["/progression/steps/0/cardView must be equal to one of the allowed values"]
cardView=tablature   total=13  new-vs-baseline=["/progression/steps/0/cardView must be equal to one of the allowed values"]
```

**Почему это критично.** Цепочка автосохранения:

`AppStore.#notify({persist:true})` → `ProjectController.startAutosave` (`src/app/projectController.ts:124-127`) → `DebouncedAutosaveEngine.scheduleAutosave` → `executeSave` → `repo.saveProject` (`src/persistence/projectRepository.ts:77-96`) → `encodePortableProject` → **throw**.

**Сценарий отказа:** пользователь нажимает «G» в матрице → добавляет аккорд → новый шаг получает `cardView: "guitar"` → debounce 300 мс → `encodePortableProject` бросает → проект **не сохраняется вообще**. Дополнительно падают `Export Project…` (`projectController.ts:266-272`) и `Save Project As` (`:256-264`), потому что оба идут через тот же encode. После перезагрузки — старое состояние. Undo не поможет: исключение происходит вне истории.

Для гитариста это означает полностью несохраняемый проект.

**Исправление (по возрастанию правильности):**

1. Hotfix: расширить enum в схеме до `["harmonic","piano","staff","guitar","tablature"]` и добавить round-trip тест на каждое значение `CardViewId`.
2. Правильно: `cardView` шага — легаси-поле, UI его игнорирует при рендере (`ProgressionStepCard.tsx:59`). Не сериализовать его, а выводить из `presentation.globalMatrixCardView` при декоде; при этом `schemaVersion` поднять и добавить миграцию.
3. Обязательно: тест, который для каждого члена union-типа прогоняет `encode → decode` — чтобы такой дрейф ловился компилятором/тестом, а не пользователем.

**Сопутствующая находка (тоже проверено):** `presentation.globalMatrixCardView` **не валидируется схемой вообще** — `presentation` не имеет ни `additionalProperties: false`, ни описания этого поля. Probe подтвердил: `"guitar"`, `"totally-bogus-view"` и даже `42` принимаются молча. То есть в проект можно записать произвольное значение, которое затем станет невалидным `cardView` при создании следующего шага.

### 4.2 🔴 CRITICAL — ошибка автосохранения полностью проглатывается; при сбое запись теряется

**Проверено лично (чтение `autosave.ts` целиком).**

`src/persistence/autosave.ts`:

```ts
43  scheduleAutosave(project: Project): void {
44    if (this.isDisposed) return;
47    this.pendingProject = project;
50    if (this.debounceTimer !== null) { clearTimeout(...); this.debounceTimer = null; }
55    if (this.debounceMs <= 0) {
57      void this.executeSave();          // ← «void»: никто не ждёт и не ловит
59    } else {
59      this.debounceTimer = setTimeout(() => { ...; void this.executeSave(); }, this.debounceMs);
    }
  }

66  private async executeSave(): Promise<void> {
67    if (this.inFlightPromise) { await this.inFlightPromise; }
70    if (!this.pendingProject) return;
74    const toSave = this.pendingProject;
75    this.pendingProject = null;        // ← очищается ДО попытки записи
77    this.inFlightPromise = (async () => {
78      try {
79        await this.repo.saveProject(toSave);   // ← throw не обрабатывается
81        this.onSaveComplete?.(toSave);
82      } finally { this.inFlightPromise = null; }
85      if (this.pendingProject) await this.executeSave();
88    })();
90    await this.inFlightPromise;
  }
```

Три независимых дефекта в одном месте:

1. **Нет `catch`.** Любой отказ `repo.saveProject` (квота IndexedDB, ошибка encode из §4.1, закрытая БД) становится unhandled promise rejection: пользователь видит `Uncaught (in promise)` в консоли и **ничего** в интерфейсе. Статуса «не сохранено» в UI не существует.
2. **`pendingProject = null` на строке 75 до записи.** При отказе состояние уже потеряно — повторить попытку нечем, retry-очереди нет.
3. **`onSaveComplete` используется только тест-хуком** (`src/persistence/testHooks.ts`). Продакшн-подписчика на результат сохранения нет вообще.

**Исправление:** `catch` в `executeSave` с возвратом проекта в retry-очередь и backoff; не обнулять `pendingProject` до успеха; добавить `onSaveError` и индикатор «не сохранено» в UI. Также добавить `flush` на `beforeunload`/`pagehide` — сейчас изменения в пределах debounce-окна 300 мс теряются при закрытии вкладки.

### 4.3 🔴 CRITICAL — Undo переключения модуля не откатывает гармонию, но выглядит успешным

**Проверено лично: найдено перекрёстным сопоставлением, затем подтверждено чтением кода.**

`dispatcher.ts` обрабатывает **37** типов команд. Я собрал все типы, которые команды кладут в `inverse:`, — их **31**, и ровно один не обрабатывается:

```
INVERSE TYPES THE DISPATCHER DOES NOT HANDLE:  harmony/switch-module
```

`src/app/commands/harmonyContextCommands.ts:78-85` — `switchModule` возвращает inverse именно этого типа:

```ts
inverse: {
  type: "harmony/switch-module",
  payload: { destinationModule: previousModule, resolutions: Object.freeze(previousIdentities), nowIso },
}
```

А в `src/app/commands/dispatcher.ts` ветки `case "harmony/switch-module"` **нет** (есть `"harmony/set-tonic"` на строке 124 и `"harmony/restore-state"` на 165). Управление уходит в:

```ts
167    default:
168      return project;      // молча возвращает ПРОЕКТ БЕЗ ИЗМЕНЕНИЙ
```

**Сценарий отказа.** Пользователь переключает активный модуль (напр. progressions → dark-harmony). `switchModule` переписывает `harmonicFunction` каждого шага на функции нового модуля и меняет `activeModule`. Нажатие Ctrl+Z:

- `AppStore.undo()` (`src/app/appStore.ts:65-71`) вызывает `applyInverseCommand`, получает **тот же самый** проект;
- `undo()` возвращает `true` — интерфейс считает, что всё откатилось;
- `activeModule` остаётся `dark-harmony`, а шаги — с функциями нового модуля.

Ещё опаснее обратное направление: при `dark-harmony → progressions` inverse-вызов **вообще не доходит** до `switchModule`, поэтому его защита `planModuleSwitch` + `plan.resolutions.find(...)!` не срабатывает. То есть откат не просто не работает — он не проходит через код, который отлавливает неоднозначные соответствия функций.

**Корневая причина — архитектурная, а не опечатка:**

```ts
// src/app/commands/index.ts:3-6
export interface ProjectCommand<TPayload = unknown> {
  readonly type: string; // ← не union, а просто string
  readonly payload: TPayload;
}
```

`type` — обычная строка, поэтому:

- `switch (command.type)` в `dispatcher.ts` **не проверяется на полноту компилятором**;
- `default: return project` — единственный путь для любого забытого типа, и он беззвучен;
- 31 `command as SomeCommand` каст в каждой ветке (`dispatcher.ts:90-166`) отключает проверку соответствия типа и payload.

**Исправление:**

1. Сделать `type` размеченным union (`type ProjectCommand = SetTempoCommand | ... | SwitchModuleCommand`) — тогда `switch` без ветки перестанет компилироваться.
2. Заменить `default: return project` на `default:` с `never`-проверкой и выбросом ошибки: беззвучный no-op в undo-пути недопустим.
3. Немедленно добавить `case "harmony/switch-module"` → `switchModule`.
4. Регрессионный тест: для **каждого** типа, встречающегося в `inverse:`, проверить, что `applyInverseCommand` реально меняет проект.

### 4.4 🔴 CRITICAL — гитара превращает **все** минорные септаккорды в доминантсептаккорды

**ИЗМЕРЕНО.** Подагент заявил это как чтение кода; я исполнил реальный код через type-stripping Node 24 и получил следующие фактические питчи (см. §2 «метод» и §9):

```
C   major triad -> major (4 semitones)  pcs=[0,4,7]    midi=[48,52,55,60,64] style=open
Cm  minor triad -> minor (3 semitones)  pcs=[0,3,7]    midi=[48,55,60,63,67] style=barre-a
C7  dominant 7  -> major (4 semitones)  pcs=[0,4,10]   midi=[48,52,58,60,64] style=open
Cm7 minor 7     -> major (4 semitones)  pcs=[0,4,10]   midi=[48,52,58,60,64] style=open   <<< НЕВЕРНО
Am7 minor 7     -> major (4 semitones)  pcs=[0,4,7,10] midi=[45,52,55,61,64] style=open   <<< НЕВЕРНО
Dm7 minor 7     -> major (4 semitones)  pcs=[0,4,7,10] midi=[50,57,60,66]    style=open   <<< НЕВЕРНО
Bm7b5 half-dim  -> major (4 semitones)  pcs=[0,4,7,10] midi=[47,51,57,59,66] style=open   <<< НЕВЕРНО
```

**Важно: это хуже, чем было заявлено в исходной находке.** Дефект не ограничен случаем «minor + minor7». Сравнение `Cm7` и `C7` даёт **байт-в-байт одинаковый** результат — `midi=[48,52,58,60,64]` в обоих случаях. То есть любой минорный септаккорд гитара играет и рисует как соответствующий доминантсептаккорд: **Cm7 звучит как C7**, `Am7` → `A7` (терция C# вместо C), `Dm7` → `D7` (F# вместо F), `Bm7♭5` → `B7`.

Проверенный механизм — тот же, что описан ниже.

```ts
// src/domain/instruments/guitar/voicings.ts:446-448
let quality = chord.baseQuality as string;
if (chord.isMajor7) quality = "major7";
else if (chord.isSeventh || quality === "dominant") quality = "dominant";
```

Все вызывающие передают `isSeventh = baseQuality === "dominant" || variant.seventh !== undefined`:

```ts

const isSeventh =
  input.chord.baseQuality === "dominant" || input.chord.variant?.seventh !== undefined;
```

Значит для **Cm7** (`baseQuality: "minor"`, `variant.seventh: "minor7"`) выполняется `isSeventh === true` → `quality = "dominant"` → базовое качество `minor` **затирается**.

Дальше `voicings.ts:529-538` выбирает `chosenTemplate.dominant`, потому что `quality === "dominant"` проверяется раньше `minor`:

```ts
const templateConfig =
  quality === "minor"     ? chosenTemplate.minor
  : quality === "dominant" ? chosenTemplate.dominant     // ← сюда попадает Cm7
  : ...
```

**Итог:** Cm7 отображается и звучит как C7 — E вместо E♭. Аналогично Bm7♭5 → B7, B°7 → доминантовая форма. Это слышимые неверные ноты в гитарном воспроизведении, на диаграмме грифа и в табулатуре (`src/domain/instruments/guitar/tablature.ts:120` передаёт тот же флаг).

**Исправление:** не давать `isSeventh` перекрывать базовое качество. Нужны отдельные ветки для `minor + minor7` (m7-шаблоны), `half-diminished7` и `diminished7`. Обязателен тест на каждый `BaseChordQuality × SeventhKind`.

### 4.5 🟠 HIGH — Modes Explorer: превью показывает E7, Apply вставляет Em7

**ИЗМЕРЕНО** исполнением реального кода (формула `harmonic-minor-baroque`: `i → iv → V7 → i`, тоника A).

Превью-карточка строится через `computeModalChords` (`ModesExplorerModal.tsx:111`, `:477-497`) и аудируется её же питчами (`:140-160`). Применение идёт **другим путём**: `createModesFormulaSteps` (`src/app/commands/modesExplorerCommands.ts:60-77`) → `getModalParentKeyAndFunction` → `realizeChord`. Замер обеих сторон:

```
deg | PREVIEW card (computeModalChords)      | APPLY result (mapping + forced 7th)
----|---------------------------------------|--------------------------------------
  1 | Am [C-E-G#-A]                         | Am [C-E-A]
  4 | Dm7 [C-D-F-A]                         | Dm7 [C-D-F-A]
  5 | E7 [D-E-G#-B]                         | Em7 [D-E-G-B]   <<< РАСХОЖДЕНИЕ
  1 | Am [C-E-G#-A]                         | Am [C-E-A]
```

**Ступень 5 — реальный дефект с неверными нотами.** Формула объявлена как `V7` с `quality: "dominant"` (`modes.ts:1322`), превью показывает и играет **E7** (E-G#-B-D), а Apply вставляет **Em7** (E-G-B-D). Доминантсептаккорд — сама драматургическая суть harmonic minor («elevated by the dramatic leading tone in the major dominant V7», как честно написано в описании формулы на `modes.ts:1317`), и именно он теряется: G# заменяется на G.

**Механизм** (проверен по шагам):

```ts

if (modeId === "harmonic-minor" || modeId === "melodic-minor") {
  const parentTonic = normalizePitchClass(normTonic + 3); // относительный мажор
  const MINOR_SCALE_MAP = ["vi", "vii°", "I", "ii", "iii", "IV", "V"] as const;
  const functionId = MINOR_SCALE_MAP[(degree - 1) % 7] ?? "vi";
  return { parentTonic, functionId, moduleId: "progressions" };
}
```

Ступень минорного лада отображается на функцию **одноимённого мажора**. `MINOR_SCALE_MAP[4] = "iii"`, а в `progressions.ts:135-142` `iii` объявлен как `quality: "minor"` → база аккорда становится минорной (Em). Далее `formulaSeventh` (`modesExplorerCommands.ts:37-40`) приписывает септиму **minor7** (потому что символ `V7` заканчивается на «7»), и `createMatrixChordStep` мержит её в вариант. Итог: минорная терция + минорная септима = **Em7** вместо **E7**. Септима накладывается поверх уже неверного базового качества, поэтому исправление только септимы ничего не даст.

**Что здесь НЕ является дефектом** (уточняю, чтобы не расширять объём работ): ступени 1, 4, 6, 7 для harmonic minor и 2, 4, 6 для melodic minor отображаются корректно — триады относительного мажора совпадают со ступенями минорного лада. Также расхождение по ступени 1 (`Am` против `Am` с септимой) — это превью, обогащающее аккорд относительно авторского `i`; Apply верен формуле, а неверно превью. **Точный дефект — только ступени, чьё качество в гармоническом/мелодическом миноре отличается от относительного мажора: 5 (и 3/Caug) для harmonic minor, 4/6 для melodic minor.**

**Исправление:** маппить ступень на функцию минорного словаря (`i`, `ii°`, `III`, `iv`, `V`, `VI`, `vii°`) вместо словаря относительного мажора, либо строить шаг напрямую из `computeModalChords`, чтобы превью и результат шли одним путём и такое расхождение стало невозможным по построению. Первое — минимальная правка в одной функции; второе — устранение класса дефектов.

## 5. Что сделано хорошо

Аудит был бы неполным без этого раздела: качество здесь заметно выше среднего для проекта такого размера, и часть решений стоит **сохранить, а не переписывать**.

1. **Точное рациональное время как единственный семантический источник.** Инвариант «1 каноническая доля = четвертная» выдержан: `duration.ts:29-37`, `meter.ts:107-114`, `timeline.ts:39`, `measureLayout.ts:107-114`. `rationalToNumber` встречается **только** на границах (секунды аудио, пиксели) — утечки float в семантику я не нашёл. Это правильное решение, и оно защищает от целого класса дефектов.
2. **Экранные координаты не являются источником истины.** Явный контракт в `ProgressionTrack.tsx:2219-2221`: «The visible handle can sit inside a centered Staff event, far from the musical endpoint. Only its movement, never its absolute x, changes time». Реализовано через `screenXToAbsoluteResizeEndpoint` + snap. Это устраняет дрейф при zoom/scroll — редкая зрелость.
3. **Валидация на обеих границах persistence.** `encodePortableProject` валидирует документ **до** записи (`portableProject.ts:573-582`), `decodePortableProject` — **после** миграций (`:640-649`). Схема строгая: `additionalProperties: false` в 25 местах, 16 обязательных полей верхнего уровня, `schemaVersion` через `const`.
4. **Корректный MIDI-writer.** VLQ реализован верно (`writer.ts:57-66`), дельта-времена корректны, note-off сортируется перед note-on на общем тике (`compareEvents:96-104`), каналы валидируются 0..15, вывод **побайтово детерминирован** и покрыт golden-hex тестом.
5. **MusicXML-writer проверяет проекцию до вывода** и сверяет Rational ↔ MusicXML duration через **BigInt** (`writer.ts:94-146`) — без усечения и округления. Полное экранирование XML (`writer.ts:37-67`).
6. **`SampleCache` — качественная реализация** (`sampleCache.ts:71-137`): LRU с честным учётом байт, дедупликация in-flight загрузок, допуск одного сверхбюджетного буфера, восстановление после ошибки без «отравления» кэша.

8. **`measureDeletion.ts` — образец дисциплины:** «сначала докажи эквивалентность таймлайна, потом применяй», с атомарным отказом и явными сообщениями о конфликте инструментов (`:588-625`, `:1022-1061`, `:1341-1360`).

### Дополнительно по запросу: двухцветная клавиатура и повторные ноты

Виртуальная клавиатура (видна на скриншоте внизу) подсвечивала все играющие клавиши одним
голубым, так что по цвету нельзя было понять, какая рука что играет, а две одинаковые подряд
идущие ноты выглядели как одна длинная.

- **Два цвета.** Мелодия — правая рука (голубой), верхние голоса аккорда и бас — левая
  (янтарный). Разделение берётся из `channelRole` уже готового события (`melody` против
  `upper`/`bass`), никакого нового анализа не добавлено. Ключ, который звучит в обеих руках
  одновременно (мелодия дублирует тон аккорда), получает цвет мелодии, чтобы не мигал между
  руками. Цвет не единственный носитель смысла: на клавише есть `data-hand`, а `aria-label`
  произносит «melody (right hand)» / «chord or bass (left hand)». В панели управления добавлена
  легенда из трёх образцов.
- **Повторная нота.** Если та же высота зазвучала снова, клавиша вспыхивает белым кольцом
  (класс `is-rearticulated`), сохраняя свой цвет руки, — то есть «какая рука» и «сыграно
  заново» читаются независимо. Повтор определяется сравнением **onsets**: у удержанной ноты
  onset не меняется, у новой — меняется. Для `prefers-reduced-motion` анимация отключается, но
  статичное кольцо остаётся, так что признак не теряется.

**Найденная при этом ошибка:** первая версия сохраняла _самый ранний_ onset среди голосов на
одной высоте. Из-за этого легатный повтор мелодии поверх тянущегося аккорда был неотличим от
удержания — onset не менялся. Исправлено на _самый поздний_ onset (последний удар), проверено
прогоном: повтор даёт `[72]`, удержанная нота — `[]`, память не растёт (1 запись после 5000
кадров). Память onset'ов живёт в `ref` компонента и возвращается из чистой функции, а не в
модульной переменной, поэтому две клавиатуры на экране не мешают друг другу.
